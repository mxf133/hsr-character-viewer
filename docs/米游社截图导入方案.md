# 米游社「观星一览」截图导入方案（2026-10-21）

> 分支 `feat/android-client`。目标：让安卓用户把米游社 App 生成的**角色总览分享长图**
> （「开启旅情!」/观星一览，含全部角色 + 星魂数）导入本程序，替代登录。
> 样图：1264×7917，用户 2026-10-21 提供。全部结论**已用样图实测**，
> 实验固化在 `tools/_probe-mys-share-card.mjs`（复现命令见文末）。

---

## 1. 这张图上到底有什么（逐点解剖）

```
┌──────────────────────────────────────┐
│ 开拓者「光明火柴」   UID: 107987102    │ ← 头部：昵称 + UID +「已与66名角色邂逅」
│ ✦ 在游戏中已与66名角色邂逅            │    （总数字 = 天然的识别对账校验）
├──────────────────────────────────────┤
│ [卡] [卡] [卡]  ×22 行               │ ← 卡片网格，3 列
├──────────────────────────────────────┤
│            米游社 logo  [QR]         │ ← 底部二维码（见 §2，不是数据捷径）
└──────────────────────────────────────┘
```

单张卡片（实测坐标，原图 1264 宽）：

```
┌─────────────┬──────────────┐
│ [元素][命途] │ Lv.80 ❖ 2    │ ← 白panel顶：等级 + 星魂数（格式恒定）
│  角色立绘    │              │
│  (暗色区)    │  [光锥卡面]   │ ← 叠影罗马数字角标（Ⅰ~Ⅴ）；没装光锥 = 空占位圈
│ 名字(白字)   │  ★★★★☆      │ ← 光锥无名字文字，只有卡面美术
└─────────────┴──────────────┘
```

关键事实（全部实测）：

1. **角色名印在图上**（白字描边，固定字体，高对比）——识别「是谁」靠 OCR 而不是认脸；
2. **`Lv.80 ❖ 星魂数` 格式完全恒定**——数字识别几乎不会错；
3. 有 **5★（金底）/ 4★（紫底）两个区段，几何不同**——不能写死网格 pitch，要用连通域找卡；
4. 名字会出现**词典外条目**：样图里实际印着「银狼LV.999」（boss/活动变体）与「Archer」「Saber」
   （联动角色）——纯词典匹配必须有兜底；
5. 没装光锥 = 白panel 右侧是空占位圈，可直接检测「无光锥」；
6. 头部总数字（66）是**免费的完整性校验**：识别出的卡片数必须对上。

## 2. 先排除一条捷径：底部二维码不是数据入口（实测）

* jsQR 解码成功 → `https://mhyurl.cn/bd0kFBAL`；
* 302 跳转到 `webstatic.mihoyo.com/app/community-game-records/rpg/index.html#/rpg`
  （米游社「战绩」H5），**短链与跳转 URL 都不带任何数据参数**；
* 该 H5 的数据走 `api-takumi-record.mihoyo.com/game_record/*`（与本程序同族接口），
  **需要登录态**才出数据。

结论：二维码只是 App 引流入口，不能当结构化数据源。但它仍有用：**解码出短链 ≠ 数据，
解码流程本身可以在导入时顺便校验图是真的米游社分享图**（模板特征之一）。

## 3. 推荐方案：浏览器端识别（手机上全自动 + 人工确认）

### 3.1 架构：识别放前端，服务端零新增依赖

```
手机浏览器（安卓/iOS 通吃）
  1. 用户在虚拟账号页选「从米游社截图导入」→ <input type=file> 选长图
  2. canvas 解码 + 网格切分（§3.2 的连通域算法）
  3. 逐卡 OCR：名字条（中文+拉丁）、Lv/星魂条（数字）—— WASM OCR，模型首次下载后缓存
  4. 词典模糊匹配：OCR 文本 ↔ 角色中文名词典（/api/archive 已有 theherta i18n）
     编辑距离 ≤2 命中 → 直接过；未命中 → 标黄交给用户（银狼LV.999 这类）
  5. 【人工确认表】每行：识别名 / 星魂 / 置信度，可改可删可忽略 ← 必须有，识别率≠100%
  6. 确认 → POST /api/virtual-accounts（现有接口！）生成虚拟账号
服务端
  不改任何识别逻辑，只复用现有虚拟账号接口 + 下发角色词典。零新增 npm 依赖。
```

选「浏览器端」的理由：① 与 §6 手机端方案天然衔接（Termux / 远程服务端都只需要浏览器）；
② WASM OCR 模型由 CDN/SW 缓存，不进仓库；③ 安卓 iOS 一套代码；④ 服务端保持零依赖。

### 3.2 网格切分算法（已验证原型）

1. 行投影：统计每行「亮度 < 150」的像素数，阈值 + 最短 120px → 卡片行带
   （样图实测 pitch 320/320/321，非常稳）；
2. 列投影：任取中间行带统计列密度 → 3 列 portrait 的 x 跨度（样图 [95,270],[462,637],[829,1005]）；
3. **生产版改为连通域**：金底/紫底两区段几何不同、边界行可能丢（样图探针得 63 张，
   头部宣称 66，差的正是边界行）——按「白panel 圆角矩形」或「portrait 色块」做连通域
   就能两个区段一把抓；
4. 名字条 = portrait 底缘（暗带结束线下 ~50px）；Lv 条 = 白panel 顶（格式 `Lv.NN ❖ N`）。

### 3.3 OCR 选型

| 引擎 | 中文 | 体积 | 备注 |
| --- | --- | --- | --- |
| **tesseract.js（chi_sim）** | 可 | ~12 MB 模型 | 生态最省事，首推第一版 |
| PaddleOCR wasm（det+rec mobile） | 强 | ~10 MB | 更准，第二版换装 |
| ML Kit 中文 OCR | 强 | 系统级 | 只在 §6.2 的原生 APK 里用，浏览器用不了 |

OCR 的活其实很轻：名字 ≤6 个字、数字 3~4 个、字体恒定。字典只有 ~200 个角色名，
编辑距离纠错后可用率预计很高；**真正的底线是 §3.1 第 5 步的人工确认表**。

### 3.4 光锥识别（二期，可先留空）

光锥名字不印在图上，只能认卡面美术：官方光锥卡面图 CDN 已在用（界面本来就要显示），
canvas 里对「卡面区域」算 pHash，与官方图库逐一比对（汉明距离阈值）。叠影罗马数字
（Ⅰ~Ⅴ）5 个模板直接匹配。识别不出就留空让用户手填——**一期先只导角色+星魂**，
已经覆盖「算补金方案」的主需求。

### 3.5 校验器（导入可信度的三道闸）

1. **数量对账**：识别卡数 == 头部 OCR 出的「已与N名角色邂逅」，不等 → 提示重拍/重试；
2. **UID 对账**：头部 UID 与用户输入/已有账号比对；
3. **同名去重**：正常截图不会有两个「银狼」（样图的「银狼LV.999」是不同名字），
   OCR 后同名多卡 → 必是识别错误，标出来让用户裁决。

## 4. 备选路线（为什么不用）

| 路线 | 结论 |
| --- | --- |
| A. 二维码 → 结构化数据 | **实测否决**：短链无数据参数，H5 要登录态（§2） |
| C. 安卓原生 ML Kit App | 等做原生 APK（§6.2 v2）时顺路做，识别管线与 3.1 完全同构 |
| D. 服务端识别（Node 里跑 OCR） | **否决**：破坏「零第三方依赖」根基；且 Termux 手机上跑 WASM OCR 太重 |
| E. 不识别，用户手填虚拟账号 | 现状兜底，保留；截图导入是它的自动化 |

## 5. 落地顺序与工程量

| 步骤 | 内容 | 量级 |
| --- | --- | --- |
| 1 | 本文档 + 探针入库（`tools/_probe-mys-share-card.mjs`） | 本轮已做 |
| 2 | 前端：文件选择 + canvas 切分 + 切条预览（无 OCR，先让用户肉眼核对切分对不对） | 中 |
| 3 | 前端：tesseract.js 接入 + 名字/数字识别 + 词典模糊匹配 + 人工确认表 | 大（一次搞定） |
| 4 | 确认表 → `POST /api/virtual-accounts`（复用现有接口，可能要加一个「自由名单」变体） | 小 |
| 5（二期） | 光锥 pHash 匹配 + 叠影模板 | 中 |

## 6. 与手机端方案（v2 文档）的关系

* 本功能是 §4.2「iOS 快捷指令导入」的**替代上位方案**：不用快捷指令、不用 DS 签名，
  用户只要能截图就能导入，安卓 iOS 通吃；
* 也是「不想登录米游社」用户的个人化入口（风险为零——图片是自己 App 生成的，
  导入全程不碰米游社接口）；
* 识别管线若未来进原生 APK（ML Kit），浏览器版与原生版共用同一套切分/匹配/确认表设计。

## 7. 复现实验

```bash
# 探针（切分 + 对账 + 二维码 + montage），modules 目录需先 npm install --prefix 那里 jpeg-js jsqr
node tools/_probe-mys-share-card.mjs <分享长图.jpg> --modules=<node_modules 目录> --out=<输出目录>
# 样图实测输出：21 行带 × 3 列 = 63 卡（边界行差 3 张，见 §3.2-3）、行 pitch 320/321、
# 底部二维码 = https://mhyurl.cn/bd0kFBAL（→ 战绩 H5，无数据参数）
```
