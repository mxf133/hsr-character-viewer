## 0. 一句话概括

把现在「**5 关卡加权** × **6 版本加权** × 强度/性价比/**泛用性** 三旋钮」的模型，换成
「**单关卡选择** × **版本加权** × 强度/性价比 **两旋钮**」，投稿粒度统一收敛到 `frontier`（配装层），
并把**全部评分计算搬到 Node 服务端**，浏览器只负责渲染 + 分页 + 搜索请求。

这是「简化」而不是「加法」：现在 `advice.js` 里存在**三条互相独立、基准不一致**的打分链
（`byRoster` 的 Tier 链 / `avTeams` / `allTeams`），长期没法对齐。新模型只有**一条**。

## 2. 数据层：`frontier` 必须扩列（这一步是地基）

### 2.1 现在 `frontier[]` 的三个硬伤

现每行只有 `{c(金数), a(比较值), t(档位), m(成员)}`。要支撑新算法缺三样东西：

| 缺什么 | 后果 |
|---|---|
| **没有原始行动值** | `a` 是被 builder 统一过的 comparable：**轮次型关卡（混沌/虚构/异相仲裁）里 `a` 是轮次**（0~10），而新上场率要按「300 / 500 **行动值**」分档 → 判据直接失效 |
| **没有真实投稿数** | 同一配装+成本被去重合并了（`herta-build.mjs:634` `fkey`），`count` 算出来了（`:661`）但**输出时被丢掉**（`:828-` 只留 `c/a/t/m`）。上场率若按行数计，会把配装变体数当人数 |
| **只收 `perfect`/`target` 档** | 见下表，「通关」这一类现在只覆盖 **67%~92%** 的投稿 |

### 2.2 覆盖率实测（`theherta/archive.json`，2026-10-18）

```
混沌回忆 4.5   投稿 503    frontier 462   覆盖 92%
绝境     4.5   投稿 512    frontier 421   覆盖 82%
绝境     4.6   投稿 312    frontier 235   覆盖 75%
末日幻影 4.5   投稿 553    frontier 381   覆盖 69%
虚构叙事 4.3   投稿 389    frontier 262   覆盖 67%
```

结论：**frontier 现在不等于「全部投稿」**，缺的是 `pass` / `below`（打得慢但通关了）那批。
上场率要统计「通关」，这批不能丢——否则「通关」饼图和「0T」饼图会长得几乎一样，
第 3 类第 4 类也就失去意义了。

### 2.3 改造清单（改 `tools/herta-build.mjs`）

| 改动 | 位置 | 状态 |
|---|---|---|
| 放开 tier 过滤：`if (tier === 'perfect' \|\| tier === 'target')` → `if (tier !== 'unknown')` | `:627` | ✅ 已改 |
| 输出 `n`（真实投稿数） | frontier 输出段 | ✅ 已改 |
| ~~补 `rav` / `r` 字段~~ | — | ❌ **不需要了**，见下 |

**为什么不用补 `rav`**：重新读了 builder 才确认，`action_value` 在 builder 里已经**分模式**算过一遍
（`:414-419`）——末日 = `4000 − 积分`，绝境 = 真实 `action_value`，**其余模式 = `metric`（轮次）**。
所以 `frontier.a` 这个字段本身就已经是「行动值型给行动值、轮次型给轮次」的正确值，
而用户第 5 条又把轮次型改成了轮次口径 ⇒ **只有行动值型需要行动值，而它恰好已经有了**。
省掉两个字段、也省掉一次全量重 Build。

### 2.4 ✅ 重建结果（2026-10-18 已跑）

`theherta/raw/submissions/` 有 64 个文件 27 MB，`herta-build.mjs` 纯本地聚合，**离线重跑 2.5 秒**：

```
frontier 行数   26102 → 27901
投稿总数        Σn = 30627
覆盖率          67%~92% → **100%**（逐关卡核对：每一关 Σn 都等于 runCount）
缺 n 的行       0
档案体积        23.7 MB → 23.12 MB（反而小了：teams 侧是体积大头，frontier 增量远小于预估计）
```

关键对照：**行数 27901 ≠ 投稿数 30627**。这正是 §5.1 里上场率必须按 `n` 累加的依据——
同一套阵容常被拆出十几种配装变体，按行数计会把热门角色刷虚高。

`baseline` 复核（放开 tier 后应当不变，实测确实不变）：混沌 4.5 = 2、绝境 4.5 = 9，与重建前一致。
**唯一例外**：末日幻影 4.4 从 1 变成 0 —— 是 0 金队混进 baseline 了，已由 §5.1.1 的两条规则修掉。

## 3. §一 · 投稿得分

### 3.1 关卡选择（5 选 1，默认绝境）

沿用现有 `advice.js:1504` `ENV_WEIGHT_ROWS` 的清单，但**从权重输入框改成单选**：

| # | mode | stage | 中文名 | 判据类型 |
|---|---|---|---|---|
| 1 | `aa` | `plight` | 异相仲裁 · 绝境 **[默认]** | 行动值 |
| 2 | `as` | `` | 末日幻影 | 行动值 |
| 3 | `aa` | `` | 异相仲裁 | 轮次 |
| 4 | `moc` | `` | 混沌回忆 | 轮次 |
| 5 | `pf` | `` | 虚构叙事 | 轮次 |

### 3.2 基准最低金 `baseline(v)` —— 逐版本算

```
行动值型  baseline(v) = min{ c(f) | f ∈ frontier(v), rav(f) < 500 }
轮次型    baseline(v) = min{ c(f) | f ∈ frontier(v), r(f) == 0 }
```

**实测（最近 6 版的最低达标金）**：

| 关卡 | 4.1 | 4.2 | 4.3 | 4.4 | 4.5 | 4.6 |
|---|---|---|---|---|---|---|
| 绝境 | 11 | 7 | 10 | 7 | **9** | 8 |
| 末日幻影 | 2 | 2 | 1 | 1 | **2** | 3 |
| 混沌回忆 | 1 | 1 | 1 | 1 | **2** | — |
| 异相仲裁 | 3 | 2 | 3 | 1 | **1** | 1 |
| 虚构叙事 | 2 | 3 | 2 | 1 | **3** | — |

这个表**本身就是结论**：绝境的入场券是 **7~11 金**，其它关卡 **1~3 金**。
它很好地解释了「为什么绝境能看到 E2 强势」——便宜的配置在这里根本达标不了。

### 3.3 投稿得分（照你的公式，逐字实现）

```
行动值型： strengthPart = Ws × max(0, 1 − rav / 500)
轮次型：   strengthPart = Ws × 1 / (r + 1)

costPart   = baseline(season(f)) / c(f)          // ∈ (0, 1]，比值量纲
投稿得分   = strengthPart + Wc × costPart
```

几点说明（都照字面，没有自作主张加东西）：

- 强度项已经乘了 `Ws`，投稿得分里只给成本项乘 `Wc` —— 与你写的「强度得分 = 强度权重 × (…)」一致，
  默认 1:1 时两条式子对称。
- 实测存在 `rav ≥ 500` 的行吗？**绝境 4.5 → 0 条**（分布 0~499，中位 290），
  末日 4.5 → 0 条（分布 0~300）。所以当前数据下 `max(0, …)` 不会触发。
  但放开 tier 过滤后会进来慢速投稿，**这个 clamp 是必需的**，保留。
- `costPart` 上限为 1（自己就是最低金时拿满），不会出现 >1。

### 3.4 边缘用例（先写好，别等爆）

| 情况 | 处理 |
|---|---|
| 该版本无达标投稿 → `baseline` 取不到 | 该版本的 `costPart = 0`，**但分母仍计入**（等同于「已上线无得分」） |
| `c(f) = 0` | 数学上无意义，实际数据最低 1 金；运行时 `if (!(c>0)) skip` |
| `rav` 缺失 | 只算进「通关」类，不进达成度分类 |

### 3.5 角色整包得分

整包 = `{角色, 星魂档 E0/E1/E2/E6, 光锥, 叠影}`，沿用 `advice.js:4039` `packKeyOf`。

```
整包某版本得分 = max{ 投稿得分(f) | f 包含该整包, f.version = v } × versionWeight(v)

整包得分 = Σ_v 整包某版本得分 / Σ_v 生效 versionWeight(v)
```

**分母规则**（照你写的两种情况）：

- 版本 v 在窗口内 & 整包**未上线**（`debut(v_pack) > v`）→ **分子分母都不计**
- 版本 v 在窗口内 & 整包**已上线但无投稿** → **分子记 0，分母计入**

登场版本取 `src/server/character-debut.js:57` `CHARACTER_DEBUT_VERSION`，
缺表时用 `archive.refs.firstSeen` 兜底。**注意**：现有代码里这张表只用于排序、不进评分，这次要正式进评分。

比较口径：**全部 / E0 / E1 / E2 / E6**（`EIDOLON_TIERS = [0,1,2,6]`，`advice.js:2222`），保持不变。

## 4. §二 · 抽卡方案

### 4.1 补金推荐分（按确认过的第 1 条）

```
Δgold = 账号补到这一行配装所需金数（复用现有 marginalCostOf，advice.js:2130）

costPart' = clamp( baseline(v) / Δgold , 0, 1 ]      Δgold = 0 时取 1（已经齐了 → 满分）

补金推荐分 = ( strengthPart + Wc × costPart' ) × versionWeight(v)
```

Δgold = 0 直接给满分，避免除零，也符合直觉：你已经有的东西，补它成本为 0。

### 4.2 补金明细（fill）

沿用 `advice.js:3580-3604` 的贪心拓扑排序（按 `perPull = value / pullsExpected`，
含「光锥跟在载体之后」的约束 `:3594`）。这套是验证过的，不动。

### 4.3 过渡档位 / 次选档位

沿用现有概念，只是核算基准换成新的扣分制：

- **过渡档位**（`mid`，`advice.js:3687`）：把 fill 切成前半段（≤ ∆gold/2），未买的成员退回账号现状
- **次选配队**（`alternatives`，`advice.js:3737`）：共享成员 ≥2 的邻队，倒排索引 `byMember` 加速，取前 3

### 4.4 全量参与 + 全量可搜索 —— 服务端为主

```
GET /api/gacha/postings?env=aa:plight&ws=1&wc=1&hidden=…&account=<id>&q=<kw>&sort=score&page=1&size=20
```

- Node 端**一次遍历**给全部投稿算分（10 万条约几十 ms），结果按
  `(env, ws, wc, hidden, accountVersion)` 签名缓存在内存
- 搜索 = 服务端对已建好的**角色名倒排索引**做 AND 匹配（复用 `advice-paging.js:63 queryTermsOf` 的切词规则）
- 前端只收当前页（20 条）+ 总数 + 虚拟滚动
- 排序：服务端排好，前端 `withRealRank`（`advice-paging.js:142`）保留真实名次

**为何不在浏览器端算**：这是本地服务，延迟可忽略，但浏览器要把 10 万条 × 配装塞进内存 + 排序，
首屏就得几百 ms 到几秒。服务端算一次缓存，后续所有翻页/搜索都是 <10 ms。

## 5. §三 · 环境统计 · 上场率（重做）

### 5.1 四类口径（嵌套，各自独立一份 Top10）

数据源 = `frontier`（放开 tier 过滤后 = 全部投稿），**按 `n`（真实投稿数）累加**，不是行数。

**按关卡类型分两套判据**（用户第 5 条：轮次型改轮次口径）。

**行动值型** —— 绝境·王棋关、末日幻影

| 类别 | 判据（`a` 在此已经是行动值） |
|---|---|
| 通关 | 全部 frontier 行 |
| 小于 300 行动值 | `a < 300` |
| 300 ~ 500 行动值 | `300 ≤ a < 500` |
| 0T | `a === 0` |

**轮次型** —— 混沌回忆、虚构叙事、异相仲裁（骑士关）

| 类别 | 判据（`a` 在此就是轮次） |
|---|---|
| 通关 | 全部 frontier 行 |
| 0T | `a === 0` |
| 1T | `a === 1` |
| 2T 及以上 | `a ≥ 2` |

嵌套关系（如你确认的）：**行动值型** `0T ⊂ <300 ⊂ 通关`、`300~500 ⊂ 通关`；
**轮次型** `0T ⊂ 通关`，三档轮次互斥。四类各出一张饼图，切换查看。

> **为什么必须分两套（实测依据，不是推测）**：
> `tools/herta-build.mjs:406-419` 的注释早就写明 ——
> 「站点的 `action_value` **只有异相仲裁绝境王棋关那一批真的填了**，其余模式是 null 或空串」。
> builder 因此给轮次型回落到了 `metric`（轮次）。也就是说 **轮次型关卡根本没有行动值可查**，
> 「300 / 500 行动值」在混沌/虚构/异相仲裁上是无源的判据 → 只能换口径。你这条判断是对的。

> ⚠️ **轮次型存在严重的投稿自选择偏差**（实测混沌回忆 4.5，按 `n` 计）：
> `0T: 481  1T: 3  2T: 7  3T: 8  4T: 3  5T: 1`（合计 503）
> **0T 占 95.6%** —— 玩家基本只投稿打得好的那几把。所以「1T」「2T+」两张饼图样本会是
> 个位数到十几条。这不是 bug，是数据本来的样子；UI 上要**明示样本量**，避免被误读。

### 5.1.1 ⚠️ `cost = 0` 的 0 金队（会炸除法，必须防御）

放开 tier 后实测发现 **19 行 `c = 0`**（全四星队，真实存在，如
`Clara + 开拓者(记忆) + 停云 + 加拉赫`；分布：混沌 7 行 / 末日 12 行）。
后果：若不过滤，`baseline` 会被拉到 0，所有队伍的 `costPart` 一起变 0。

两条规则配套解决：

```
baseline(v) = min{ c(f) | 达标行 f ∈ frontier(v), c(f) > 0 }     ← 剔除 0 金
costPart(f) = c(f) > 0 ? clamp(baseline / c(f), 0, 1] : 1        ← 0 金队拿满分
```

0 金队给满分符合直觉：它比 baseline 还便宜，本来就该是最省的那一档。

### 5.2 饼图设计（依赖无关 → 手写 SVG 环形图）

仓库现在**没有任何图表基础设施**（全仓无 `conic-gradient` / `createElementNS` / canvas），所以新写。

技术选型：**环形图（donut）而不是扇形 pie**。理由：用 `<circle>` + `stroke-dasharray` 组合，
每段一个 circle，动画只需要动 `stroke-dashoffset`（GPU 友好、纯 CSS 可做），
比 `<path>` 扇形弧好写十倍，而且环形中心天然留出一个放角色信息的洞。

```
        ┌─────────────────────────┐
        │      ╭─────────╮        │
        │    ╭─╯         ╰─╮      │   ① 载入：整圈从 0° 扫出（600ms ease-out）
        │   │   ┌─────┐    │      │   ② hover：该段放大 1.04 + 提亮，其余降透明度到 .35
        │   │   │ 头像 │    │      │   ③ 中心联动：角色中文名 / 次数 / 占比 / 命途
        │   │   └─────┘    │      │   ④ 图例：右侧 Top10 列表，与环一一 hover 联动
        │   │  12.4%       │      │   ⑤ 切版本/切类别：中心数字做补间过渡（不是直接跳）
        │    ╰─╮         ╭─╯      │
        │      ╰─────────╯        │
        │  ▣ Xxx    ▣ Yyy   ▣ 其它 │
        └─────────────────────────┘
```

- 前 10 名各一段 + **「其它」合并成第 11 段**（灰紫色，放在最后，视觉上退出主叙事）
- 配色：10 个色相均匀拉开 + 第 11 段中性灰；**浅色主题**（跟随 IDE light theme）
- 动态效果：`prefers-reduced-motion` 时全部降级为直接显示，不闪
