# 黑塔网增量同步「漏投稿」审计

> 2026-10-21，分支 `audit/herta-sync-coverage`。只读审计 + 一个可复跑的探针
> `tools/_probe-sync-coverage.mjs`。**同日已按 §5 实施修复（v4.6.136），见文末 §7。**

## 0. 结论先行

**会漏，而且此刻已经在漏。**

- 本地数据集共 30846 条投稿，其中**已缺 11 条**：`4.5 虚构叙事`少 10 条（本地 255 / 线上 265，
  该期少 3.8%）、`4.5 异相仲裁`少 1 条（1749 / 1750）。这 11 条按现在的判据**以后也不会再抓**。
- 漏的机制是「期一结束就永久跳过」，而黑塔网**在期结束后很久还会放出投稿**。
- 另有一个更严重的独立问题：**增量同步从不刷新 `submission_config.json`**，线上已经排到 4.7，
  本地排期还停在 4.6 —— 新版本对增量同步是「不存在」的。

| 编号 | 问题 | 后果 | 严重度 |
| --- | --- | --- | --- |
| R1 | 期结束后没有补抓窗口（`expireDate` 一过就永久跳过） | 每期丢最后几天到几周的投稿；丢的恰好是**最新一期**（版本权重最高） | 已在漏，每期复现 |
| R2 | 增量同步不刷新排期文件 | 新版本永远不在 `seasons` 里；线上 4.7 已存在，本地完全看不见 | 11-02 起整期数据断流 |
| R3 | 抓回来的 `items` 无条件覆盖本地文件 | 站点偶发返回空列表 → 整期清零，且被标记为「已同步」永不重抓；`raw/` 不进 git、留档也不含 `raw/` | 概率低、不可逆 |
| R4 | 「同步回来就是 0 条」也算已同步 | 站上事后补录的期永远停在 0（3.x 有 14 个组合是 0 条） | 同上 |

## 1. 判据原文

`tools/herta-update.mjs` 的 `planTargets()`（第 131~191 行）决定抓谁：

```
抓   = 从未同步过（文件不存在 / 不是 JSON）
     ∪ 该副本最新的一期（latestByMode）
     ∪ 这一期的 expireDate >= 今天
跳过 = 其余全部（已同步过、且这一期已结束）
```

三个输入决定一切：**本地文件是否存在**、**副本内最大版本号**、**排期里的 expireDate**。
**没有任何一条判据看「本地文件有多旧」** —— 这就是「很久没更新，一次更新只补最新版本」的成因。

## 2. 实测（2026-10-21 18:20 前后）

```
node tools/_probe-sync-coverage.mjs
```

- 计划交叉验证：脚本自己报 `total=5`，探针按同一判据重算也是 5 → ✓ 一致（重算可信）。
- 对 **59 个被跳过的组合**逐个拉线上条数对拍：56 个一致，**2 个少数据**。

| 组合 | 本地 | 线上 | 差额 | 末次抓取 | 期结束 |
| --- | --- | --- | --- | --- | --- |
| 4.5 / Pure Fiction | 255 | 265 | **+10** | 10-15 | 10-19 |
| 4.5 / Anomaly Arbitration | 1749 | 1750 | **+1** | 10-14 | 10-04 |

漏掉的是什么（逐条对 id）：

- `4.5 Pure Fiction` 的 10 条全是 `video_date` 10-16~10-18 的投稿 —— 季末最后几天，
  且清一色是 `0-Cycle` / `full stars`（最值钱的那一类）。
- `4.5 Anomaly Arbitration` 的 1 条 `video_date` 是 **2026-09-29**（期内），
  但期在 10-04 就结束了、我们在 10-14 抓过它，这条到 10-21 才出现在站上 ——
  **说明站方的收录/审核会滞后两周以上**，「expire 一过就冻结」的假设不成立。

另外两条边界已排除，不必再怀疑：

- 接口**不是分页**：`count === items.length`（4.5 异相仲裁 1750/1750，4.5 虚构 265/265）。
- 线上**没有本地多得多的组合**：59 个组合里没有一个出现「本地 > 线上」。

## 3. 排期漂移：增量同步根本看不见 4.7

```
本地排期：3.0 … 4.5, 4.6
线上排期：3.0 … 4.5, 4.6, 4.7      ← 线上多一个 4.7
线上 4.7：Memory of Chaos 2026-11-02 ~ 2026-12-14
排期漂移：4.6 Memory of Chaos 本地 2026-11-02~12-14 → 线上 2026-09-28~11-02
```

`src/server/archive-update.js` 的更新链只有三步：`herta-update.mjs` →
`herta-availability.mjs` → `herta-build.mjs`。**唯一会拉 `submission_config.json` 的是
`tools/herta-fetch.mjs`（全量 56 MB），而它只被当成「首次采集」的手工步骤**（见
`src/server/app.js` 里那些「尚未采集资料，请先运行 herta-fetch」的提示）。
所以界面上点「更新数据」永远学不到新版本。

后果比 R1 更硬：`latestByMode` 会一直停在 4.6，11-02 之后混沌回忆的新投稿全部记在线上 4.7 名下，
本地连文件名都没有。

## 4. 用户问的两个场景，分别是什么答案

1. **「版本更新后刚好没更新到旧版本最后几天上传的数据」** —— 会漏，且是**必然**。
   期一过 `expireDate`、且该副本已有更新的一期，这个组合就被永久跳过；
   最后一次抓取只可能发生在 `expireDate` 当天或之前，之后的投稿（当天的下半段、
   以及站方滞后两周才放出来的）全部丢失。这正是上表的 11 条。
2. **「很久没更新，一次更新只更新最新版本，旧版本完全错过了」** ——
   **文件缺失的不会漏**（`neverSynced` 会把 64 个组合里缺的一次补齐），
   但**有旧文件的会永久停在那个残缺快照**：判据不看文件年龄，抓过一次就算「同步过」。
   例：8 月抓过 4.4 虚构（当时 200 条），10 月才回来同步，4.4 虚构永远停在 200 条。

## 5. 修法建议（2026-10-21 当日已全部实施，见 §7）

按收益/成本排序。三个改动的量级都是「每次同步多几个请求」，不是重写。

### R2：同步开头刷一次排期（40 KB，1 个请求）

在 `herta-update.mjs` 读 `submission_config.json` 之前，先从 `/submission_config.json`
拉一份、与服务端同源比对后落盘（失败就沿用本地并打警告，不阻断同步）；
同时把 `submission_config.json` 加进 `archive-update.js` 的留档清单
（现在只留 `archive.json` / `unit-availability.json` / `manifest.json`，第 108 行）。

### R1：给「期已结束」加宽限 + 轮转清扫

```js
const GRACE_DAYS = 30;   // 期结束后这段时间内继续重抓：盖住「季末最后几天」+「站方滞后两周」
const SWEEP = 2;         // 每次同步额外重抓 N 个「最久没抓过」的已结束组合
```

- `expireDate + GRACE >= 今天` ⇒ 抓。今天这个口径下会多抓 3 个组合
  （4.5 虚构 10-19、4.5 异相 10-04、4.5 末日 10-05），正好把那 11 条捞回来。
- 宽限期过后仍可能补录（3.x 现在还有 14 个 0 条组合），所以再从「已跳过」里按
  文件 mtime 升序取 `SWEEP` 个强制抓一次：59 个组合约 30 次同步轮完一圈，
  每次只多 2 个请求（约 3 MB）。
- 这样「很久没更新」也自动修好：断更 3 个月后回来，凡是在这期间过期、
  且从没在宽限期内抓过的组合，都会各补一次。

### R3/R4：覆盖前看一眼条数

`fetchOne()` 拿到 `items` 后，与本地 `existing` 比较：**新条数比旧的少就不覆盖**，
保留旧文件并回报警告（线上 59 个组合的实测都是只增不减，所以「变少」几乎一定是故障）。
不要指望 `herta-build.mjs` 的缩水保护兜底：它的下限是**总量** 50%
（`SHRINK_FLOOR`），单期清零只掉 5.7%，照样过。

### 代价估算（今天的真实数据）

| 方案 | 每次同步的抓取组合数 | 请求量 |
| --- | --- | --- |
| 现在 | 5 | 约 1.3 MB |
| + 宽限期 | 8 | 约 2.6 MB |
| + 轮转清扫 2 个 | 10 | 约 5.5 MB |
| + 排期文件 | 10 + 1 | 约 5.6 MB（+40 KB） |

## 6. 补回这 11 条

```bash
node tools/herta-update.mjs --all && node tools/herta-availability.mjs && node tools/herta-build.mjs
```

`--all` 会重抓 64 个组合（约 56 MB、几分钟），但它**只补当下**：
不改判据的话，下一期结束还会再漏一次。

## 7. 落地记录（v4.6.138，2026-10-21）

§5 的三项全部实施，外加留档清单：

* 判据加宽限期（`--grace`，默认 30 天）+ 轮转清扫（`--sweep`，默认 2 个/次，
  按文件 mtime 最旧优先）；两个开关用非负整数解析（0 = 显式关闭）。
* 同步开头 `refreshConfig()` 刷排期，失败只警告不阻断；`archive-update` 留档清单
  补上 `submission_config.json`。
* 缩水护栏：`count < existing` 时不覆盖本地文件、上报 `shrunk` 明细
  （`--allow-shrink` 显式接受）；退出码仍为 0。
* 实测真实数据：计划从「抓 5 / 跳过 59」变「**抓 11 / 跳过 53**」（约 6 MB/次），
  宽限期正好覆盖 4.5 三个刚结束的期 —— 下一次同步就会自动把这 11 条捞回来。
* `herta-sync-test.mjs` 断言 29 → 59 项全绿（新增 (e) 宽限/清扫、(f) 缩水护栏、
  (g) 排期刷新三节；既有用例固定跑 `--grace=0 --sweep=0` 钉住旧判据）。
